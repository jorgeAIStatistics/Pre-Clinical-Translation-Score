# Validation Plan

**Preclinical Translational Risk Scorer — how the model is evaluated, and why that design**

This document describes the evaluation design, the diagnostics that accompany
it, the residual leakage channel that is deliberately left open, and the checks
that enforce each invariant. It is written for a reviewer whose job is to find a
reason not to trust the model, so it leads with the things most likely to be
wrong.

Its companion, [MODELING_PLAN.md](MODELING_PLAN.md), justifies the estimator
itself. Read together: that document argues for the model, this one argues for
the yardstick — and reports what the yardstick actually measured.

> **Demonstration data.** Every number below comes from a **synthetic**
> demonstration cohort (600 programs, 765 development tracks, 5,273 evidence
> items) generated by `trs/seed/generator.py`. Gene symbols, target classes and
> indication names are real public vocabulary; all program-level facts and
> outcomes are simulated. Nothing here is an empirical claim about real
> therapeutic programs, and nothing here constitutes regulatory or clinical
> validation.

## 1. Why a random train/test split is meaningless here

Not merely optimistic — meaningless. `trs/validation/splitters.py` states three
independent reasons, and each is handled structurally rather than hoped away.

**One biological bet appears many times.** The same program is developed in
three indications; the same target is attacked by four sponsors; the same
molecule is renamed twice. Random splitting puts near-duplicates of the test
rows into training, and the model learns to recognise the program rather than to
assess the evidence. On the demonstration cohort, 552 rows reduce to **465**
independent units under the loosest defensible grouping — an 18% reduction before
any stricter definition is applied.

**The deployment task is prospective.** The product scores a program at a
decision point using only what is then known, to predict something that has not
happened yet. A cross-sectional split trains on 2019 programs to predict 2011
outcomes, which is not the task and does not measure the capability being sold.

**Grouping keys overlap transitively.** Grouping on the program id alone misses
one asset carrying two development codes. The correct object is a connected
component, not a key (§2).

The consequence is stated once, in the report document itself, so no reader can
miss it (`assemble_report` → `evaluation_design.statement`):

> "No random train/test split is reported anywhere in this document, because on
> this problem it would be optimistic by an unquantifiable margin."

### The headline design

`temporal_split` (`trs/validation/splitters.py`) partitions on the as-of date,
then enforces component integrity **on top of** the date boundary. A component
whose rows straddle a boundary is assigned **wholly to the later partition** and
its earlier rows are dropped. Assigning to the later side is the conservative
direction: it removes rows from training rather than letting future-resolved
siblings inform an earlier prediction.

On the registered model `ptrs-pef-007`:

| | |
|---|---|
| Protocol | `temporal_outer_maturity` — **not** permitted to describe its numbers as deployment performance |
| Protocol rejected first | `strict_temporal`: 0 usable folds once per-fold label maturity applies |
| Split manifest hash | `165cb164f07e18e7…` |
| As-of date range | 2005-03-24 → 2021-12-26 |
| Assessment boundary (76th percentile of admissible as-of dates) | 2017-09-04 |
| Fitting origin = label cutoff | 2017-09-04 |
| Corpus data cutoff | 2026-10-13 |
| Development | 187 |
| …of which received an out-of-fold selection prediction | 122 |
| Dedicated calibration slice | 0 (calibrator fitted on grouped out-of-fold predictions covering all 187 development rows) |
| Evaluation (locked, read once) | 127 (70 positive, prevalence 0.551) |
| Purged: outcome unresolved at the data cutoff | 24 |
| Purged: component straddled the assessment boundary | 12 |
| Purged: label not yet knowable at the fitting origin | 202 |

Each splitter reports how many rows it discarded to preserve its invariant, and
that number belongs in the report: a split that quietly throws away a third of
the cohort to stay clean is telling you the cohort is small. Component
straddling costs 12 rows (2.2%), which is cheap. **Label maturity costs 202**,
which is not — it is the single largest exclusion in the pipeline, and it is
the price of not training on outcomes that had not happened at the origin the
fit claims. The median outcome lag on this cohort is 5.3 years.

Hyperparameter selection uses `forward_chaining_folds` — expanding windows
*inside the development partition*, each fitting its own feature transformer on
its own permitted rows — so neither tuning nor family selection can see the
evaluation partition, and no inner fold is encoded using constants derived from
its own held-out rows.
See [MODELING_PLAN.md §9](MODELING_PLAN.md#9-hyperparameter-selection).

## 2. Connected-component grouping

`ConnectedComponentGrouper` builds a union–find (disjoint-set) structure over
the active grouping keys. Two cohort entries land in the same component if they
share any key in scope, **or are linked through a chain of such shared keys**.
Splitters then assign whole components, which guarantees no unit spans a
boundary. Path compression is applied on `_find`, and components are relabelled
to compact integers so the report is readable.

The transitive closure is the point. Grouping on program id alone would keep
"program A under code X" and "program A under code Y" in the same fold only by
accident; joining on compound id as well, and taking the closure, keeps them
together by construction.

**The cost is granularity**, and `summary()` surfaces it so a reader can see
when the effective sample size for validation is much smaller than the row
count. On the demonstration cohort under the identity scope:

| | |
|---|---|
| Rows | 552 |
| Components | 465 |
| Largest component | 3 |
| Median component size | 1.0 |
| Singleton components | 374 |

This is a benign case: the largest component is 3 rows, so folds remain fine
grained. `_limitations()` in `trs/pipeline/train.py` adds a limitation bullet
whenever the largest component exceeds 15% of the cohort; it did not fire here.
The artifact nonetheless records the headline honestly: *"Validation rests on
465 independent connected components, not 552 rows."*

## 3. The two group scopes, and why they cannot be combined

**Identity is not similarity, and the distinction decides the split.** Two
sponsors developing different CDK4/6 inhibitors are not the same program; they
are the same *bet*. Conflating the two is the single most consequential choice
in this evaluation design, so two scopes are defined and both are reported.

### `GroupScope.IDENTITY` — program + compound

The same asset under a different name. This is unambiguous leakage, so it is
enforced on the **headline temporal split**.

It stops there deliberately. An analyst at a 2018 decision point genuinely knew
the outcomes of 2010 programs on the same target; removing that knowledge would
make the training distribution differ from the serving distribution, and the
model would be evaluated on a task it will never be asked to perform.

### `GroupScope.STRICT` — program + compound + target

Stricter than deployment requires, used for a **secondary, clearly-labelled
sensitivity analysis** (`_target_grouped_sensitivity` in
`trs/pipeline/train.py`). It answers one question: how much of the model's
performance comes from memorising target-level outcomes rather than from reading
the evidence for the individual program?

### Why they cannot be combined — measured, not asserted

Under strict grouping a target's programs span the whole time range, so
components straddle every temporal boundary. Applying the headline temporal
split to strict components on this cohort gives:

| Scope | Components | Largest | Straddle the 2017-12-23 boundary | Temporal split: train / test / dropped |
|---|---|---|---|---|
| Identity (program, compound) | 465 | 3 | **12 of 465** | 187 / 127 / 238 |
| Strict (+ target) | 42 | 23 | **39 of 42** | **31 / 540 / 403** |
| + mechanism class | 8 | 245 | — | **0 / 552 / 434** |

A 31-row training set is not a training set. The incompatibility is a property
of the problem, not of the implementation, and the report states it rather than
silently picking one. The strict analysis is therefore run as a **cross-sectional
grouped 5-fold** and labelled as such in the artifact
(`target_grouped_sensitivity.design`).

**Mechanism class is never a grouping key.** Taking the transitive closure over
mechanism swallows the cohort: 552 rows collapse to **8** components, the largest
holding 245 rows, and the temporal split degenerates to zero training rows. It is
also conceptually wrong — it would remove from training exactly the class-level
information a real analyst possesses. Mechanism remains available as the grouping
*variable* for the hierarchical model, which is a different purpose entirely.

> **Note on a stale figure.** The docstring of `trs/validation/splitters.py`
> reports the mechanism-grouping collapse as "211 rows into 9 components". That
> figure is from an earlier, smaller cohort. On the cohort backing
> `ptrs-pef-007` the measured figure is **552 rows into 8 components**, largest
> 245. The qualitative conclusion is unchanged and stronger; the number in the
> docstring should be refreshed.

### What the sensitivity analysis found

`target_grouped_sensitivity`, 5-fold over 42 strict components, all 552 rows
scored out-of-fold, calibration fitted inside each fold on a held-out slice of
that fold's own training data:

| Metric | Strict grouped 5-fold | Headline temporal split |
|---|---|---|
| AUROC | 0.642 | 0.622 [0.515, 0.718] |
| Brier | 0.237 | 0.238 |
| Log loss | 0.654 | 0.731 |
| Scaled Brier | +0.021 | +0.035 |
| Calibration slope | 1.066 | 0.851 |

The AUROC gap of 0.029 is the headline result: removing all target-level
co-membership costs a little discrimination but does not collapse it. Two
cautions on reading it. First, the two designs differ in more than grouping —
one is temporal and one is cross-sectional — so the difference is not a clean
attribution to target memorisation alone. Second, the confidence intervals
overlap heavily; on this data the comparison cannot resolve a 0.03 AUROC
difference.

### Leakage is asserted, not assumed

`leakage_audit()` runs after every split the report uses, and `train()` raises
`RuntimeError` if it comes back unclean. On `ptrs-pef-007`:

```
component: 0   program: 0   compound: 0   →  clean: true
informational overlap (not enforced): target 39, sponsor 25, mechanism 13
```

Overlap on keys **outside** the active scope is reported as context, not treated
as a defect. Knowing that 39 targets appear on both sides of the temporal
boundary is useful — it is the quantity the strict sensitivity analysis exists
to probe — but it is not, by itself, leakage under the estimand being measured.

## 4. Component-level bootstrap

Every interval in the validation report resamples **connected components**, not
rows (`component_bootstrap_indices`). Resampling rows independently would treat
the three indications of one program as three independent observations and
produce intervals too narrow by roughly the square root of the mean component
size.

The same unit is used for the paired model-comparison test
(`paired_bootstrap_difference`), which is **paired** because both models see the
same programs: comparing two independent intervals would discard the shared
variation and badly overstate the uncertainty in the difference.

On `ptrs-pef-007`: 500 replicates requested, unit = `connected component`,
level = 0.95, and all 500 were usable for every metric
(`primary_metrics.bootstrap`, and `n_bootstrap: 500` on each estimate). Replicates
that draw fewer than 10 rows or only one outcome class are discarded rather than
scored; an estimate backed by fewer than 20 usable replicates is reported
without an interval rather than with a fabricated one.

On this cohort the component effect is mild — 465 components from 552 rows,
median size 1 — so component and row intervals would be close. That is a
property of this dataset, not a general result. On a cohort with larger
components the difference would be the dominant correction, which is why the
component unit is the default rather than an option.

## 5. The usefulness gate

**This is the threshold question**, and it is the one an AUROC headline hides.
A model can discriminate slightly while producing probabilities that are, on
average, further from the truth than simply quoting the cohort attrition rate to
everyone. In that state it must not be presented as decision support.

`_usefulness_verdict` (`trs/pipeline/train.py`) evaluates the **scaled Brier
score** — the Brier skill score against the no-covariate base-rate model,
`1 − BS/BS_base` — together with its component-bootstrap interval, and assigns
one of four verdicts: `beats_base_rate` (interval entirely above zero),
`worse_than_base_rate` (entirely below), `not_distinguishable_from_base_rate`
(straddles zero), or `indeterminate`.

The verdict is written into the artifact and surfaced on the Methods page **and
in every API score response**. It is not a diagnostic buried in an appendix.

### What it found

```
verdict: not_distinguishable_from_base_rate
Brier skill −6.5%  (95% CI −21.5% to +5.9%), interval includes zero.
"Treat individual estimates as weakly informative at best."
```

The platform says this about itself, in its own output, on its own demonstration
data. That is the intended behaviour. A scoring platform that cannot report its
own lack of skill is a worse artefact than one with no skill.

## 6. The metric panel

`evaluate()` in `trs/validation/metrics.py` returns a full panel, ordered so
that calibration and utility outrank discrimination. The ordering is a
deliberate statement: a committee comparing 35% against 70% is reading the
numbers, not the ranking.

### Evaluation-partition performance, `ptrs-pef-007` (n = 127, 70 positive)

| Group | Metric | Value | 95% component-bootstrap CI |
|---|---|---|---|
| Discrimination | AUROC | 0.622 | [0.515, 0.718] |
| | AUPRC | 0.673 | [0.566, 0.792] |
| Accuracy | Brier | 0.238 | [0.213, 0.265] |
| | Log loss | 0.731 | [0.637, 0.825] |
| | **Scaled Brier** | **+0.035** | **[−0.065, +0.112]** |
| Calibration | Slope | 0.851 | [0.165, 1.615] |
| | Intercept (slope fixed at 1) | −0.229 | [−0.538, +0.127] |
| | ECE (10 quantile bins) | 0.098 | — |
| | MCE | 0.220 | — |

**Why calibration outranks AUROC for this product.** AUROC is invariant to any
monotone distortion of the probabilities. A model whose every prediction is
halved has an unchanged AUROC and a worthless output. The calibration slope of
0.851 says the deployed model is over-confident on the evaluation partition — predictions
too extreme in both directions — even after logistic recalibration. The
intercept of −0.229 says predictions are slightly too high overall. Both are
reported with intervals, and the slope interval [0.213, 1.390] is wide enough
that the model's calibration is itself poorly determined at this sample size.

Two implementation details matter for reading these numbers:

- The calibration **intercept is estimated with the slope fixed at 1**
  (calibration-in-the-large), which is the standard definition. Estimating both
  jointly conflates two distinct failure modes.
- ECE uses **quantile** binning by default. Equal-width bins leave most bins
  nearly empty when predictions concentrate, producing a calibration plot
  dominated by noise in regions holding three observations. Each bin also
  carries a **Wilson** interval on the observed rate, which behaves sensibly at
  0 and 1 — and calibration bins frequently sit at 0 or 1.

### Decision-curve net benefit

The right question for a portfolio committee is not "is the AUROC good" but "if
I deprioritise every program above X% predicted risk, am I better off than
deprioritising all of them or none of them?". `decision_curve()` answers exactly
that:

```
NB = TP/n − (FP/n) · (pt / (1 − pt))
```

where the threshold `pt` encodes the committee's own exchange rate between a
wrongly killed good program and a wrongly funded bad one. A model is useful over
the range where its curve sits above **both** reference strategies.

On `ptrs-pef-007` (evaluation prevalence 0.551), the model's net benefit exceeds both
`treat_all` and `treat_none` at thresholds **0.40, 0.45, 0.50, 0.55 and 0.60**:

| Threshold | Model NB | Treat-all NB | Treat-none NB |
|---|---|---|---|
| 0.35 | +0.303 | +0.319 | 0 |
| 0.40 | +0.264 | +0.262 | 0 |
| 0.45 | +0.217 | +0.195 | 0 |
| 0.50 | +0.161 | +0.114 | 0 |
| 0.55 | +0.133 | +0.016 | 0 |
| 0.60 | +0.101 | −0.107 | 0 |
| 0.65 | −0.013 | −0.266 | 0 |

Below 0.40 flagging everything is at least as good. Above 0.60 the model's net
benefit oscillates around zero (−0.013 at 0.65, −0.027 at 0.80, +0.007 at 0.90),
which at these counts is noise, not a high-threshold operating region. The
honest summary is a **narrow band of usable thresholds around the prevalence**,
which is consistent with — and should be read alongside — the usefulness verdict
in §5, not in place of it.

Threshold metrics (sensitivity, specificity, PPV, NPV, flagged fraction) are
reported at 0.3 / 0.5 / 0.7 so a reader can see the operating points directly
rather than inferring them from a curve.

## 7. The diagnostic suite

Four checks in `trs/validation/report.py` exist specifically to catch
self-deception.

### 7.1 Coefficient sign audit

Compares each fitted coefficient's sign with the direction pre-registered in the
feature registry. `UNCERTAIN` features are exempt; one-hot and missing-indicator
columns are skipped because they carry no directional prior.

A sign flip is **not automatically wrong** — it may be a real finding,
confounding, or a data bug — but it must be seen rather than averaged into an
aggregate. Only discordances whose credible interval excludes zero are treated
as material.

On `ptrs-pef-007`: **56 checked, 21 discordant, 0 credibly discordant.** Every
discordant interval straddled zero. Example: `animal_mean_disease_similarity`
was declared `decreases_risk` and fitted at +0.039 with an interval of
[−0.095, +0.174] — an unresolved sign, not a contradicted one. That profile is
what a heavily shrunk model with little signal should produce, and it is
consistent with the usefulness verdict.

`train()` logs a warning whenever `n_discordant_credible` is non-zero.

### 7.2 Domain ablation

Refits the whole pipeline with each of the 12 feature domains removed in turn
and reports the change in held-out performance. A domain whose removal costs
nothing is not contributing to the estimate, however prominent it is in the
interface. The refits use the same calibration design as the main model, so the
comparison is like-for-like.

| Domain | Features removed | Δ log loss vs full | Δ AUROC vs full |
|---|---|---|---|
| PK/PD translation | 6 | **+0.0152** | −0.0323 |
| Reproducibility & study quality | 9 | **+0.0118** | −0.0150 |
| Target validation | 6 | **+0.0107** | −0.0462 |
| Animal-model validity | 10 | +0.0012 | +0.0055 |
| Safety translation | 4 | +0.0006 | +0.0015 |
| Program context | 4 | +0.0001 | +0.0035 |
| Evidence volume & recency | 3 | −0.0002 | +0.0013 |
| Human biological support | 5 | −0.0023 | +0.0020 |
| Cross-species concordance | 5 | −0.0024 | +0.0120 |
| **Historical class performance** | **4** | **−0.0027** | **+0.0015** |
| Biomarker readiness | 3 | −0.0051 | +0.0011 |
| Disease-model relevance | 4 | **−0.0129** | **+0.0252** |

Positive Δ log loss means removal **hurt**. Three domains carry the model's
signal on this data: PK/PD translation, reproducibility, and target validation.
Nine do not, and two — disease-model relevance most clearly — are actively
*harmful*: removing disease-model relevance improved held-out log loss by 0.013
and AUROC by 0.025. On a 127-row evaluation partition those deltas are well inside noise and
should not be over-read, but they do mean no domain can be described as
"contributing" on this data without qualification.

### 7.3 Interval agreement

Re-derives prediction-interval widths by nonparametric bootstrap refit (40
component-level resamples of the training partition, 30 probe rows) and compares
them with the analytic Laplace widths on the log-odds scale. Agreement within
±25% is treated as acceptable; systematically narrower analytic intervals would
mean the published uncertainty is optimistic.

On `ptrs-pef-007`: median ratio (analytic ÷ bootstrap) **1.90**, p10 1.55,
p90 2.44, verdict **`analytic_intervals_too_wide`**. The published intervals are
conservative by roughly a factor of two — the safe direction, but a real finding
discussed in [MODELING_PLAN.md §6.5](MODELING_PLAN.md#65-how-honest-are-the-intervals).

Note the asymmetry in how this is surfaced: `_limitations()` adds a limitation
bullet for `analytic_intervals_too_narrow` but not for `..._too_wide`, so this
run's verdict lives only in the diagnostic. That is a defensible priority (too
narrow misleads; too wide merely costs sharpness) but it means the artifact's
`limitations` list is not a complete account of the diagnostics.

### 7.4 Subgroup reporting with a minimum-n floor

Performance within each level of modality group, target-class group, evidence
completeness tertile and era. An aggregate metric can hide a model that works
for small molecules and is noise for cell therapies.

`MIN_SUBGROUP_N = 15`. Below that — or where a level has only one outcome class —
the level is reported with `reported: false` and an explicit reason rather than
with a number. Publishing an AUROC from 5 programs invites over-reading, and
suppressing the row entirely hides that the subgroup exists at all; the code
does neither.

Selected reported levels from `ptrs-pef-007`:

| Variable | Level | n | AUROC | Scaled Brier | Calibration slope |
|---|---|---|---|---|---|
| Modality | `small_molecule` | 88 | 0.689 | +0.090 | 1.13 |
| | `antibody` | 31 | 0.671 | +0.060 | 0.83 |
| Target class | `immune` | 23 | 0.785 | +0.183 | 2.73 |
| | `kinase` | 60 | 0.703 | +0.094 | 1.34 |
| | `surface_antigen` | 34 | 0.537 | **−0.093** | **−0.07** |
| Completeness | `low_completeness` | 38 | 0.715 | +0.128 | 1.91 |
| | `mid_completeness` | 55 | 0.582 | −0.006 | 0.42 |
| | `high_completeness` | 56 | 0.564 | **−0.057** | 0.28 |
| Era | `2016–2021` | 143 | 0.617 | +0.022 | 0.66 |
| | `2012–2016` | 6 | — | — | not reported (n < 15) |

Two of these deserve a reviewer's attention. On `surface_antigen` the model is
*worse than the base rate* (scaled Brier −0.093) with a **negative** calibration
slope — i.e. its ranking is inverted on that subgroup. And performance is
**inversely** related to evidence completeness: the low-completeness tertile
scores better than the high-completeness tertile on every measure. Both are
within noise at these counts, and neither is explained by anything in the
pipeline. They are exactly the kind of finding a subgroup table exists to
surface, and neither would be visible in the headline.

## 8. The oracle benchmark

**Reporting a metric without its attainable ceiling invites over-reading.** A
reader told "AUROC 0.63 on demonstration data" cannot tell whether that is a
pipeline recovering most of an attainable signal or a pipeline failing on an
easy problem. The two readings lead to opposite decisions.

Because the simulation knows each track's *true* failure probability,
`oracle_benchmark()` (`trs/seed/diagnostics.py`) computes the maximum attainable
performance directly: score every track by the probability the generator
actually used. Nothing can beat that, because nothing can know more than the
generator did.

| Reference | AUROC | Brier | Log loss |
|---|---|---|---|
| **Oracle** (true generating probabilities) | **0.782** | 0.185 | **0.549** |
| Deployed model (locked evaluation, n = 127) | 0.622 | 0.263 | 0.731 |
| Base rate, no covariates | 0.500 | 0.242 | 0.678 |

(n = 552 for the oracle and base-rate rows; mean true probability 0.595,
SD 0.208.)

The ceiling is well below 1.0 **by construction**, because outcomes are
Bernoulli draws from those probabilities. That is the point: a demonstration
dataset on which a model scored 0.97 would be advertising a capability the
product does not have.

**The three rows are not on a common sample**, and the difference matters for
how they are read: the oracle and base-rate rows cover all 552 labelled tracks,
while the model row is the 127-row evaluation partition. They are indicative of
the same picture but should not be subtracted from one another.

Two like-for-like statements can be made. The gap between oracle and base rate
on the full cohort — 0.592 vs 0.678 log loss, **0.086 nats** — is the *entire*
budget of learnable signal in this simulation. On the held-out partition alone,
the model's log loss of 0.671 sits **0.016 nats** below the base-rate log loss
computed at the test partition's own prevalence (0.687). The model is therefore
recovering a small single-digit-percentage share of an already modest budget,
which is exactly what the usefulness verdict in §5 says in Brier units.

The remaining gap between model and oracle is the combined cost of measurement
noise in the evidence, non-disclosure, finite sample size and model
misspecification — not a defect of the pipeline.

**Ground truth lives on disk, never in the database**
(`artifacts/demo_ground_truth.json`, carrying its own `_warning` field). A real
deployment has no ground-truth column, and adding one for the demo would create
a column the serving code could accidentally learn to read.

This benchmark exists **only** for the synthetic demonstration cohort. On real
data there is no oracle, and the appropriate substitutes — an inter-rater
ceiling, a published prior-art benchmark — must be argued for separately.

## 9. The residual leakage channel, left open on purpose

`trs/features/historical.py` computes four features: target prior failure rate,
target prior program count, mechanism-class prior failure rate, indication prior
failure rate. These are among the most predictive features available and the
easiest way to destroy a model's validity. Three distinct leaks are possible:

1. **Future outcomes** — counting a 2019 failure when scoring a 2014 decision.
   **Closed unconditionally:** the index admits only outcomes whose
   `outcome_date` precedes the cutoff.
2. **Self-inclusion** — counting the focal program's own outcome in its own
   feature, which makes the label perfectly recoverable. **Closed
   unconditionally:** every query excludes the focal track and its sibling tracks
   from the same program (`exclude_program_id`).
3. **Fold contamination** — a test-fold program contributing to a training-fold
   program's historical rate, and vice versa. **Deliberately left open.**

Leak 3 is left open because closing it would be wrong. At the historical
decision point the analyst genuinely did know about other companies' resolved
programs, including ones that happen to land in another cross-validation fold.
Removing them would make the training distribution differ from the deployment
distribution, and the model would be tuned for a world that does not exist. What
matters is that no *future* information enters and that the focal program's own
fate never does — both of which are enforced.

**The consequence is that grouped folds are not fully independent through this
channel**, and the ablation quantifies it. On `ptrs-pef-007`, removing the whole
historical-class-performance domain **improved** held-out log loss by 0.0027 and
AUROC by 0.0015 (§7.2). On this data the channel carries no measurable
advantage, so the residual dependence costs nothing that can be detected. That
is a result about this synthetic cohort, not a general guarantee; the ablation
must be re-read on every retraining, and if these four features ever become the
top-ranked ablation row, the channel is doing real work and the estimate should
be discounted accordingly.

Rates are beta-binomially shrunk toward the as-of global base rate with
`PRIOR_STRENGTH = 10.0` pseudo-observations, so a target with one prior program
barely moves off the base rate and one with fifty is trusted. Without shrinkage,
a single prior program produces a rate of exactly 0.0 or 1.0. When no resolved
outcomes exist before the cutoff at all, `UNINFORMED_BASE_RATE = 0.5` is used —
the maximum-entropy choice, deliberately carrying no claim about real-world
Phase II attrition.

The limitation is also written verbatim into the artifact's `limitations` list,
so it travels with the model rather than living only in this document.

### Other known ascertainment limitations

Also carried in the artifact:

- **Publicly disclosed programs are not a random sample.** Assets abandoned
  before an IND are systematically under-represented, so estimates *conditional
  on entering human development* are better supported than unconditional
  attrition estimates. This is one reason the estimand is conditional
  ([MODELING_PLAN.md §1](MODELING_PLAN.md#1-what-the-model-estimates)).
- **Trained on synthetic demonstration data.** The first limitation bullet on
  every artifact built from the demo cohort states that its coefficients,
  metrics and predictions describe a simulated data-generating process and carry
  **no** scientific interpretation about real therapeutic programs.

## 10. Leakage and invariant test checklist

Each row maps a risk to the code that enforces the invariant and to the
automated test that should cover it.

**State of the test suite, stated plainly.** `backend/tests/` currently contains
`conftest.py` and one test module, `tests/unit/test_connectors.py` (325 lines).
`tests/statistical/` and `tests/integration/` are **empty directories**. Several
source docstrings refer to tests that do not exist — most specifically,
`trs/features/temporal.py` cites
`tests/statistical/test_temporal_leakage.py`, which is not present. **No
statistical or leakage invariant below is currently covered by an automated
test.** The enforcement column is real and runs on every training run; the test
column is a specification of work not yet done, and is marked as such.

| # | Risk | Enforced by | Automated test |
|---|---|---|---|
| 1 | Post-cutoff evidence enters a feature vector | `AsOfContext` (`features/temporal.py`) is the only path to evidence rows; `TemporalIntegrityError` on violation | **Missing** — spec: `tests/statistical/test_temporal_leakage.py` (build snapshot at *T*, insert post-*T* evidence designed to move every feature, rebuild, assert bit-identical `vector_hash`) |
| 2 | Focal program's own outcome enters its historical-rate feature | `HistoricalRateIndex._group_stats(..., exclude_program_id)` on every query | **Missing** — spec: assert rate is unchanged when the focal track's outcome is flipped |
| 3 | Future outcomes enter a historical rate | `o.outcome_date <= as_of` filter on every query | **Missing** — spec: insert a post-cutoff resolved outcome, assert rate unchanged |
| 4 | Same asset under two names lands on both sides of a split | `ConnectedComponentGrouper` transitive closure over (program, compound) | **Missing** — spec: two rows sharing only a compound id must receive the same component label |
| 5 | Any group spans the train/test boundary | `leakage_audit()` + `train()` raises `RuntimeError` if `clean` is false | Runs on every training run; **no unit test** |
| 6 | Imputation medians / one-hot levels / scaling constants fitted on all data | `FeatureTransformer.fit()` is called on `split.train` only, then serialised | **Missing** — spec: assert `TransformerState.n_fit_rows == n_train` and that transform output is unchanged when test rows are perturbed |
| 7 | Hyperparameters tuned against the test set | `tune_l2` uses `nested_temporal_folds` over `X[tr]` only | **Missing** — spec: assert the tuning trace's fold indices are a subset of the training partition |
| 8 | Calibrator fitted on data it is assessed on | `cross_validated_calibration` pools out-of-fold predictions; calibration metrics come from the untouched test partition | **Missing** — spec: assert every calibration input index is out-of-fold |
| 9 | Grid search pinned to a grid endpoint | `tune_l2` sets `optimum_at_grid_boundary` and a warning string | **Missing** — spec: fit with a truncated grid, assert the flag fires |
| 10 | Degenerate isotonic endpoint bin produces an infinite log-odds | `IsotonicCalibration.probability_bound = 1/(n+2)` clip | **Missing** — spec: fit isotonic on a sample with an all-negative lowest bin, assert output ≥ bound |
| 11 | A broken model is registered because it is the incumbent | `passes_sanity()` in `pipeline/select.py`; `baseline_demoted` recorded | **Missing** — spec: inject a candidate with log loss 1.89, assert demotion |
| 12 | A challenger adopted on noise | Margin + surcharges + paired component bootstrap in `choose_family()` | **Missing**, and **the bootstrap path was not exercised on the demo run** — both challengers were disqualified on calibration slope first |
| 13 | Row-level bootstrap intervals reported as if independent | `component_bootstrap_indices` is the only resampler used | **Missing** — spec: assert interval width grows when rows are artificially clustered |
| 14 | An interval published for a family that cannot produce one | `RiskModel.posterior_logit_samples` raises `UncertaintyUnsupported` by default; `ScoringService` propagates | **Missing** |
| 15 | A model scores a snapshot built under a different feature schema | `FEATURE_SCHEMA_VERSION` checked by the artifact loader | **Missing** |
| 16 | Synthetic provenance lost downstream | `is_synthetic` propagates to `is_demonstration`; confidence grade forced to its lowest level | **Missing** |

Items 1–4 and 10–12 are the highest-value tests to write first: each guards an
invariant whose violation would silently invalidate every number in this
document.

## 11. Reproducing the numbers in this document

All commands run from `backend/` with the repository virtualenv; there is no
activated environment, so use the absolute interpreter path.

```bash
cd backend

# Oracle ceiling and base-rate references (§8).
../.venv/bin/python -m trs.cli oracle

# Registered artifacts, including retained candidates.
../.venv/bin/python -m trs.cli models

# Full rebuild: init-db -> seed -> build-cohort -> train.
../.venv/bin/python -m trs.cli pipeline

# The connector-fixture tests, which are the only tests that currently exist.
../.venv/bin/python -m pytest tests/unit -q
```

Everything in §§3–7 is read from `backend/artifacts/ptrs-pef-007.json` under
`metrics.evaluation_design`, `metrics.primary_metrics`,
`metrics.target_grouped_sensitivity`, `metrics.domain_ablation`,
`metrics.interval_agreement`, `metrics.coefficient_sign_audit`,
`metrics.subgroup_performance` and `metrics.usefulness`. The group-scope
comparison table in §3 was computed directly against the cohort in
`backend/trs.db` by applying `ConnectedComponentGrouper` and `temporal_split`
under each key set; those figures are not stored in the artifact.
