# Modeling Plan

**Preclinical Translational Risk Scorer — the statistical approach, and the argument for it**

This document states what is being estimated, which model estimates it, why that
model was chosen over more flexible alternatives, and what each choice costs.
It is written to be checked: every constant, threshold and number below is
either a named symbol in the source tree or a value read out of the registered
model artifact. Where a design decision was made in response to an observed
failure, the failure is described.

Its companion, [VALIDATION_PLAN.md](VALIDATION_PLAN.md), covers how the
resulting model is evaluated and why that evaluation design is the only
defensible one for this problem. The two documents are meant to be read
together: this one justifies the estimator, that one justifies the yardstick.

> **Demonstration data.** Every numeric result quoted here comes from a
> **synthetic** demonstration dataset (600 programs, 765 development tracks,
> 5,273 evidence items, all generated by `trs/seed/generator.py`). Gene symbols,
> target classes and indication names are drawn from real public vocabulary; all
> program-level facts, evidence values and outcomes are simulated. No number
> below is an empirical claim about real therapeutic programs, and nothing here
> has regulatory standing or clinical validation.

## 1. What the model estimates

The primary endpoint is declared in `backend/trs/cohort/outcomes.py` and is
carried verbatim into every artifact, API response and UI surface:

> Probability that a program entering human development fails to demonstrate
> sufficient efficacy to progress successfully beyond Phase II, conditional on
> not being withdrawn first for safety, pharmacokinetic, manufacturing or
> commercial reasons.

This is a **cause-specific** estimand. A program discontinued for toxicity never
had the opportunity to demonstrate efficacy, so it is neither a positive nor a
negative example for the efficacy question and is removed from the cohort rather
than coerced into a label. `NON_SCIENTIFIC_REASONS` in `outcomes.py` names the
seven discontinuation reasons that are statements about a sponsor rather than
about biology; tracks carrying one of them are excluded regardless of outcome
label.

The cost of that decision is stated rather than hidden: the resulting number is
a **conditional** probability and will understate total attrition if read as an
unconditional one. On the demonstration cohort the conditioning removes a large
fraction of the candidate pool — 765 candidates in, 552 included, 213 excluded,
with this breakdown recorded in `CohortVersion.inclusion_summary`:

| Exclusion reason | n |
|---|---|
| `outcome_excluded:phase_1_safety_failure` | 72 |
| `non_scientific_discontinuation:commercial_strategic` | 39 |
| `outcome_excluded:phase_1_pkpd_failure` | 39 |
| `non_scientific_discontinuation:portfolio_reprioritisation` | 27 |
| `non_scientific_discontinuation:sponsor_insolvency` | 20 |
| `outcome_excluded:active_no_outcome_yet` | 17 |

Of the 552 included tracks, 335 are positive (58.9%).

Everything the model sees for a track is a function of facts knowable at that
track's as-of date. That invariant is enforced at a single chokepoint,
`AsOfContext` in `trs/features/temporal.py`: feature construction takes a
context, not a database session, so no call site can reach evidence rows without
the cutoff filter. Availability is keyed on `available_at` ("when a diligent
analyst could have found this"), never on the date of the underlying experiment.

## 2. The deployed model, and why it is not a fallback

The deployed family is `L2LogisticRisk` — L2-penalised logistic regression with
an analytic Laplace posterior (`trs/modeling/logistic.py`). It is the default
because of three properties that the product depends on, not because the
alternatives were unavailable or untried. Both alternatives were fitted on the
same cohort and the same split in the run that produced `ptrs-pef-004`; see
[§4](#4-the-selection-gate).

### 2.1 Exact additive attribution

On the log-odds scale the deployed pipeline is exactly

```
logit(p) = a + b · ( β₀ + Σⱼ βⱼ zⱼ )
```

where `a` and `b` are the calibration intercept and slope (§5) and `zⱼ` is the
standardised value of design column *j*. Each feature's contribution to the
number on screen is exactly `b · βⱼ · zⱼ`. `trs/scoring/explanation.py` sums the
per-column contributions and **asserts** the identity against the model's own
`predict_logit` rather than assuming it.

This is the difference between explanation and rationalisation. A fluent
narrative generated *from* a score will sound equally convincing when the score
is wrong. A term in the arithmetic that produced the score cannot.

Because the design matrix is standardised on the **training** mean
(`FeatureTransformer` in `trs/features/transform.py`), the origin of the
standardised space is the cohort-average program, and the intercept is that
program's log-odds. Every contribution therefore reads as "how this program
differs from the cohort average" — which is the comparison a reviewer is making
anyway.

### 2.2 The L2 penalty *is* a Gaussian prior

`_fit_penalised_logistic` minimises

```
−Σᵢ wᵢ [ yᵢ ηᵢ − log(1 + e^{ηᵢ}) ]  +  ½ Σⱼ λⱼ βⱼ²
```

which is the negative log posterior under a `β ~ N(0, λ⁻¹I)` prior and a
Bernoulli likelihood. The fit is therefore a **MAP estimate**, not merely a
regularised point estimate, and the Laplace approximation

```
β | data  ≈  N( β̂ , H⁻¹ ),      H = XᵀWX + Λ,   W = diag(wᵢ μᵢ(1−μᵢ))
```

is the standard second-order approximation to that posterior evaluated at the
mode. It is not an invention of this codebase. `L2LogisticRisk.fit` builds `H`
explicitly at the converged `β̂`, inverts it through a Cholesky factorisation
with a jitter ladder (`_JITTER_LADDER = (0, 1e-8, 1e-6, 1e-4, 1e-2)`) and
retains both the covariance and its factor, so `posterior_logit_samples` draws
genuine correlated coefficient vectors rather than perturbing each coefficient
independently.

Two details are deliberate and worth stating:

- **The intercept is near-unpenalised.** `_INTERCEPT_PRECISION = 1e-6` exists
  only so the Hessian is invertible in the intercept direction. Shrinking the
  intercept would shrink the base rate, and the base rate is the one thing the
  model should not be shy about.
- **`λ` may be a vector.** The same routine serves the hierarchical family,
  which applies a separate precision to its group-effect block. Writing the
  prior as a per-coefficient precision vector rather than a scalar is what makes
  that possible without a second optimiser.

**The approximation is asymptotic, and at this sample size that is an
assumption rather than a fact.** It is therefore tested, not asserted: see
[§6.5](#65-how-honest-are-the-intervals) and the `interval_agreement`
diagnostic in [VALIDATION_PLAN.md](VALIDATION_PLAN.md#63-interval-agreement).

### 2.3 Why the IRLS is hand-written — and the check that it is right

Newton–IRLS with a backtracking line search is implemented directly in
`_fit_penalised_logistic` rather than delegated to a library. The reason is
narrow and specific: **the Hessian used for the posterior must be provably the
same matrix the optimiser converged on.** If the fit came from a library and the
Hessian were reconstructed afterwards, any divergence between the library's
penalty convention (particularly its treatment of the intercept) and ours would
silently corrupt every published interval. A second benefit is that a library's
intercept convention cannot change under us between versions.

The cost of writing it ourselves is that the fit could be wrong. So it is
checked against `sklearn.linear_model.LogisticRegression` (lbfgs, `C = 1/λ`,
`tol=1e-12`, `max_iter=20000`) on the **actual** training matrix of the
registered model — 187 development rows × 109 design columns, λ = 64:

| Quantity | Max absolute difference |
|---|---|
| Slope coefficients `β₁…β₁₀₉` | 2.85 × 10⁻⁸ |
| Intercept `β₀` | 1.63 × 10⁻⁷ |
| Predicted probability on the 127 evaluation rows | 8.54 × 10⁻⁸ |

The intercept difference is the largest of the three and is expected: sklearn
leaves the intercept completely unpenalised while this implementation applies
`1e-6`. The agreement on predictions — under 10⁻⁷ in probability — is the number
that matters, and it is far below any scale a user or a metric can see.

On that fit the optimiser converged in **4 Newton iterations**; the Hessian
condition number was **14.5**. The line search exists because separable and
near-separable folds do occur during cross-validation, and an undamped Newton
step on one of those diverges.

### 2.4 Auditability

A biostatistician can read the coefficient table, compare each sign against the
prior recorded in the feature registry, and form a view about whether the model
is behaving. `coefficient_sign_audit` in `trs/validation/report.py` automates
the first pass: it compares each fitted sign with `FeatureSpec.expected_direction`
(42 features declared `decreases_risk`, 14 `increases_risk`, 7 `uncertain` out of
63), skips one-hot and missing-indicator columns which carry no directional
prior, and reports discordances — separating those whose credible interval
excludes zero (material) from those whose interval straddles it (unresolved).

Critically, **the prior direction never constrains the fit.** A model that
silently enforces the analyst's priors cannot surprise the analyst, and
surprising the analyst is the point. On the demonstration run: 56 coefficients
carried a directional prior, 16 came out discordant, and **0** of those were
credible (every discordant interval straddled zero) — which is what a model with
this little signal should look like.

## 3. The candidate families and what each one costs

Both alternatives are fitted on every training run. Including them is what makes
"a linear model is sufficient here" a tested claim rather than an assumption.
Losing candidates are retained as **inactive** artifacts, because scoring a
program with each of them is what `specification_sensitivity` reports beside
every estimate (§6.4). They can never be served: `make_active=False` is passed
explicitly.

### 3.1 Hierarchical logistic — partial pooling

`HierarchicalLogisticRisk` (`trs/modeling/hierarchical.py`) adds partially
pooled intercepts for mechanism groups (target-class × modality-group, from
`mechanism_key_for`). The scientific motivation is real: a single global
intercept forces an ADC against a surface antigen and a small molecule against a
kinase to share a base rate, and independently fitted per-group intercepts would
chase noise with a handful of programs per group. Groups with fewer than
`MIN_GROUP_SIZE = 5` observations are folded into a shared `__small__` level
rather than each getting a column estimated from one or two rows. An unseen
group at prediction time receives a group effect of exactly zero — the
population mean — which is the correct behaviour: with no observations, the
posterior for that group's deviation is its prior.

**The honest limitation, stated in the module itself and repeated here.** This
is a penalised-likelihood (MAP) fit, not a fully Bayesian one. Group intercepts
are treated as `N(0, τ²)` by augmenting the design with group indicators carrying
prior precision `λ_g = 1/τ²`, and `τ²` is **selected on a grid**
(`DEFAULT_GROUP_PRECISION_GRID = (1, 2, 4, 8, 16, 32)`) by grouped
cross-validated log loss rather than integrated over. Shrinkage is therefore
captured correctly, but **uncertainty in the variance component itself is not
propagated into prediction intervals.** Intervals from this family are
consequently too narrow, by an amount that grows as the number of groups
shrinks. That is precisely why it is a candidate and not the default, and why
[§10](#10-what-would-justify-moving-to-full-mcmc) exists.

### 3.2 Gradient-boosted trees

`GradientBoostedRisk` (`trs/modeling/gbdt.py`) wraps
`HistGradientBoostingClassifier` with a grouped bootstrap ensemble
(`DEFAULT_ENSEMBLE_SIZE = 60`; 40 in the pipeline's default hyperparameters).
It is attractive for exactly the reason it is dangerous: it can fit interactions
the linear model cannot, and it can fit noise the linear model cannot.

Two capabilities are genuinely lost, and the class declares both rather than
papering over them:

- **No analytic posterior** (`supports_analytic_posterior = False`). Uncertainty
  comes from a bootstrap ensemble, which measures how sensitive the *fit* is to
  the training sample. That is a real quantity, but it is not a posterior
  predictive interval: it omits parameter uncertainty a Bayesian interval
  includes and systematically under-covers for small ensembles. When this family
  is deployed, `predict_with_uncertainty` attaches the caveat "Parameter
  uncertainty is estimated from a bootstrap ensemble rather than a posterior
  distribution; it is likely to under-cover" to every score.
- **No exact attribution** (`attribution()` returns `None`). Tree ensembles admit
  no exact additive decomposition. A Shapley approximation could be added, but it
  would be an approximation rendered in the same UI as an exact one with no way
  to signal the difference. Until that is solved properly this family ships with
  no driver breakdown — which is itself one of the strongest practical arguments
  for the linear default.

Its bootstrap resamples at the **group** level when groups are supplied
(`_bootstrap_indices`), so a program contributing several tracks moves in or out
of a replicate as a unit.

## 4. The selection gate

`trs/pipeline/select.py`. A more flexible model is not adopted because it scored
better; it is adopted because it scored *meaningfully* better by an amount that
survives a paired bootstrap at the component level, while remaining calibrated,
and — when it costs the product a capability — by a larger margin still.

The rules, in the order they are applied:

| Rule | Constant | Value |
|---|---|---|
| Sanity ceiling on held-out log loss | `MAX_ACCEPTABLE_LOG_LOSS` | 1.20 |
| Sanity band on calibration slope | `SANITY_SLOPE_BAND` | (0.15, 6.0) |
| Adoption band on calibration slope | `CALIBRATION_SLOPE_BAND` | (0.80, 1.25) |
| Base margin on relative test log loss | `MIN_RELATIVE_IMPROVEMENT` | 0.02 |
| Surcharge: no exact attribution | `ATTRIBUTION_LOSS_SURCHARGE` | 0.05 |
| Surcharge: no analytic posterior | `POSTERIOR_LOSS_SURCHARGE` | 0.03 |
| Statistical test | — | paired component bootstrap, 95%, must exclude zero |

**Baseline privilege, not baseline immunity.** `l2_logistic` is the incumbent
and wins ties, so noise in a 122-row development out-of-fold sample cannot decide the architecture.
But the incumbent passes the same sanity checks as everyone else. An early
version of this gate retained a baseline whose calibrator had degenerated and
whose held-out log loss was 1.89, purely because it was the incumbent; the
`passes_sanity` path and the `baseline_demoted` field exist because of that. If
the baseline fails, the best *passing* candidate is promoted; if nothing passes,
training raises rather than registering a broken model.

**Why log loss and not AUROC.** Log loss is a proper scoring rule and is
sensitive to calibration. AUROC is invariant to any monotone distortion of the
probabilities — which is exactly the failure mode that matters most for a
product whose output *is* a probability. AUROC is reported; it is not the
criterion. The gate records this reasoning in the artifact under
`gate.note`.

**Why paired and why component-level.** Both models see the same programs, so
comparing two independent intervals would discard the shared variation and
badly overstate the uncertainty in the *difference*. Rows within a connected
component are not independent, so replicates resample components
(`paired_bootstrap_difference` → `component_bootstrap_indices`). See
[VALIDATION_PLAN.md §4](VALIDATION_PLAN.md#4-component-level-bootstrap).

**The capability surcharges are a product judgement, stated rather than
hidden.** A translational risk estimate a scientist cannot interrogate is a
weaker product than a slightly less accurate one they can, so a family with no
exact attribution must clear 2% + 5% = 7%. A family whose published intervals
rest on a bootstrap approximation rather than a posterior must clear an
additional 3%. A family lacking both — GBDT — must clear **10%**. The surcharge
is a threshold, not a prohibition: a genuinely large gain still wins, and
`required_margin()` returns the itemised rationale so the artifact records why
the bar was where it was.

### What happened on the demonstration run

Recorded in `metrics.model_comparison` of `backend/artifacts/ptrs-pef-004.json`:

| Family | Test log loss | AUROC | Calibration slope | Outcome |
|---|---|---|---|---|
| `l2_logistic` | 0.6135 | 0.6516 | 0.837 | **adopted** (incumbent baseline) |
| `hierarchical_logistic` | 0.6146 | 0.6486 | 0.831 | improvement −0.2% does not clear the 2% margin |
| `gbdt` | 0.6298 | 0.5781 | 0.711 | disqualified: slope outside (0.80, 1.25) |

All three passed the wider sanity band. Both challengers were then disqualified
on the **adoption** calibration band before the margin or the bootstrap was
reached. It is worth recording what would have happened next: GBDT's relative
log-loss improvement over the baseline was **+1.03%**, against a required margin
of 10%; the hierarchical model was **worse** than the baseline by 0.09%, against
a required 2%. Neither would have been adopted on the margin either, and the
paired component bootstrap was therefore **never exercised on this run** — a gap
in coverage that [VALIDATION_PLAN.md §8](VALIDATION_PLAN.md#8-leakage-and-invariant-test-checklist)
records as an untested path.

## 5. Calibration

`trs/modeling/calibration.py` (the methods) and `trs/pipeline/calibrate.py`
(the design). The product's core output is a probability, so calibration is
mandatory here rather than optional polish: a model can rank perfectly and still
be systematically over-confident, and users act on the number.

### 5.1 The out-of-fold cross-validated design

The textbook three-way split — train / calibrate / test — is clean but
expensive. On a few hundred programs, a calibration slice large enough to fit a
stable calibrator leaves too little for training, and a small one produces a
slope estimate dominated by noise. It is worse than noisy when the split is
*temporal*, because a dedicated calibration slice is then a narrow window of
years and the calibrator learns that window's idiosyncrasies before being
applied to a different one. During development that produced a held-out
calibration slope of **0.53** — badly over-confident — even though recalibration
had nominally been applied.

So when the dedicated slice would fall below `MIN_DEDICATED_CALIBRATION_N = 200`
rows, `train()` folds it back into training and calls
`cross_validated_calibration` instead: partition the whole training set into
K = 5 **grouped** folds, fit on K−1 and predict the held-out fold, pool all K
sets of out-of-fold predictions, fit the calibrator on the pool, then refit the
model on the entire training partition and pair it with that calibrator. Every
prediction the calibrator sees is out-of-sample, and the calibrator spans the
full training time range rather than one slice of it.

**The cost, stated.** Out-of-fold predictions come from models trained on
(K−1)/K of the data and are marginally less sharp than the final model, so the
calibrator corrects for slightly more over-confidence than the final model
actually exhibits. The bias is small at K = 5 and shrinks as K grows. It is
recorded in the artifact under `calibration_selection.known_bias` rather than
corrected. On the demonstration run this path was taken with
**187 out-of-fold predictions across 5 grouped folds** and a dedicated calibration slice
of size 0.

If fewer than 40 usable out-of-fold predictions survive, the code falls back to
an **in-sample** Platt fit and writes
`"IN-SAMPLE CALIBRATION — held-out calibration metrics may be optimistic."`
into the record. It does not silently proceed.

### 5.2 Method selection, also out-of-sample

Picking between Platt, isotonic and identity on the calibration set and then
reporting that set's fit would be the same error one level up.
`select_calibrator` cross-validates *within* the calibration sample
(`StratifiedKFold`, up to 5 splits, capped by the minority-class count), then
refits the winner on the whole sample.

### 5.3 The slope-correction preference rule

`SLOPE_CORRECTION_PREFERENCE = 0.03`. If the best-scoring method is not logistic
recalibration but logistic recalibration is within 3% relative log loss of it,
logistic wins.

The justification is that a calibration sample of a few hundred rows cannot
distinguish two methods separated by a fraction of a nat — the ranking flips on
resampling — and in that regime the tie-break should not be arbitrary. Logistic
recalibration is the only candidate that corrects a calibration **slope**, and
slope error is the failure mode a temporally-shifted deployment reliably
produces. Selecting `identity` on a 0.01-nat edge leaves an over-confident model
uncorrected, which is what happened during development.

This rule fired on the demonstration run and the artifact says so:

| Candidate | CV log loss on the calibration sample |
|---|---|
| `identity` | 0.6402 |
| `logistic` | 0.6498 |
| `isotonic` | 0.6726 |

`identity` scored best; `logistic` was within 1.5% of it, so
`slope_correction_tie_break_applied: true` and logistic recalibration was
selected. The evaluation calibration slope of the deployed model is 0.851, so the
correction was warranted and still insufficient — the model remains
over-confident on held-out data, which the report states plainly.

### 5.4 The isotonic minimum-n gate

`MIN_N_FOR_ISOTONIC = 300`. Below 300 calibration observations, isotonic
regression is not admitted as a candidate at all and the exclusion is written
into `excluded_candidates` with its reason. Isotonic fits one parameter per
distinct step; on a few hundred points that flexibility mostly buys overfitting,
a step function with visible plateaus, and degenerate endpoint bins. Making the
threshold explicit is better than leaving the decision to whichever method wins
a noisy five-fold cross-validation.

On the demonstration run the calibration sample was 187, so isotonic *was*
admitted, competed, and lost on its own merits (0.6726 vs 0.6498).

### 5.5 The Laplace rule-of-succession bound

`IsotonicCalibration.probability_bound = 1 / (n_fit + 2)`.

An isotonic fit whose lowest bin happens to contain only negatives predicts
exactly zero. Taken literally that is an infinite log-odds, and a single
confidently-wrong test prediction then dominates every aggregate metric. That is
not hypothetical: during development of this pipeline, an unbounded isotonic fit
on **110 calibration points drove held-out log loss from 0.70 to 1.89**. The
model-selection sanity ceiling (`MAX_ACCEPTABLE_LOG_LOSS = 1.20`) was added at
the same time and for the same reason.

The fix is a sample-size bound rather than an arbitrary epsilon. From *n*
observations one cannot justify a probability more extreme than roughly
`1/(n+2)` — the Laplace rule of succession. Output is clipped to
`[bound, 1−bound]`, so a 110-point calibration set may assert at most 0.9%, not
0.0001%. The bound is serialised with the calibrator so a reloaded artifact
behaves identically.

### 5.6 What is and is not propagated

`LogisticRecalibration` retains the 2×2 parameter covariance from its own IRLS
fit, so calibration uncertainty flows into the prediction interval.
`IsotonicCalibration` has no such parameterisation:
`supports_parameter_uncertainty` is `False`, and when it is selected the scoring
layer attaches an explicit caveat that calibration uncertainty is **excluded**
from the interval. It does not invent one.

Logistic recalibration also composes cleanly with the additive decomposition —
every contribution simply scales by the slope `b` — which is a second, product-level
reason to prefer it.

## 6. Uncertainty

`trs/modeling/uncertainty.py`. Three sources enter the published interval and a
fourth is measured separately.

### 6.1 The three sources

- **`parameter`** — uncertainty about the coefficients given the training data.
  Drawn from the Laplace posterior for the linear families (`N(β̂, H⁻¹)`, sampled
  through the retained Cholesky factor so correlations are respected), or from
  the grouped bootstrap ensemble for GBDT, which is a different and narrower
  quantity and is labelled as such.
- **`imputation`** — uncertainty from features this program does not have. Each
  of `M = DEFAULT_N_IMPUTATIONS = 25` imputations fills the gaps with an
  independent draw from that feature's observed **training** distribution, so the
  spread across imputations is exactly the cost of not knowing. A program with a
  complete evidence package contributes zero here; a sparse one contributes a
  lot. This is what makes the interval widen for the right reason, and the
  resulting caveat names the count: "*k* of 61 numeric features are unobserved
  for this program".
- **`calibration`** — uncertainty in the mapping from model score to
  probability. Propagated for logistic recalibration by drawing `(a, b)` from
  their analytic covariance; excluded, and reported as excluded, for isotonic.

`DEFAULT_N_PARAM_SAMPLES = 400`. The defaults are chosen so a single score takes
well under a second while Monte-Carlo error on an interval endpoint stays below
roughly half a percentage point.

### 6.2 Ablation on the log-odds scale, and why not the probability scale

Components are reported by **ablation**: each source is varied alone with the
other two held at their point estimates, and the standard deviation of the
resulting **log-odds** is recorded.

The log-odds scale is used for a specific reason. The logistic link compresses
probability differences near 0 and 1, so the same amount of underlying ignorance
produces a much narrower probability-scale band for a program estimated at 5%
than for one estimated at 50%. Ablation widths measured in probability units are
therefore not comparable between programs — and not even comparable between
components for the *same* program, because the ablated point estimates sit at
different places on the curve. Log-odds standard deviations are comparable in
both directions, which is what makes a statement like "imputation dominates this
program's uncertainty" meaningful.

The interval itself is still reported in probability units (quantiles of the
sigmoid-transformed draws), because that is what a user reads. The two scales
serve different purposes and the code keeps them separate.

### 6.3 `variance_share` is an approximation, and says so

`variance_share` normalises the squared component standard deviations to sum to
one. It is **not** an exact variance decomposition: the sources interact, so the
components do not decompose the total. The total (`total_sd_logit`) is therefore
computed directly from the joint draws and is **never** reconstructed from the
shares. The dataclass docstring records this; so does the module docstring.

### 6.4 Specification disagreement is reported separately, not folded in

`specification_sensitivity()` scores the same evidence with each retained
candidate family and reports the absolute differences beside the interval — not
inside it.

Folding them in would be model averaging, and model averaging requires a prior
over model specifications. Nobody has stated one. Asserting one silently would
be exactly the kind of unearned precision this platform exists to avoid. A user
who sees "the deployed model says 61%, the tree model says 68%" learns something
a widened interval would have obscured: that the estimate depends on modelling
choices, not only on the evidence.

This is the reason losing candidates are registered as inactive artifacts
(§3). Without them the panel has nothing to compare against and reports
"unavailable".

### 6.5 How honest are the intervals?

The Laplace approximation is asymptotic. `interval_agreement` in
`trs/validation/report.py` tests whether the asymptotics has arrived at this
sample size: it refits the model on 40 component-level bootstrap resamples of
the training partition, measures the spread of predictions for 30 probe rows,
and compares that width with the analytic width on the log-odds scale.
Agreement within ±25% is treated as acceptable.

On the demonstration run the median ratio (analytic ÷ bootstrap) was **1.88**
(p10 1.55, p90 2.44), verdict **`analytic_intervals_too_wide`**. The published
intervals are therefore roughly twice as wide as a bootstrap refit suggests they
need to be — conservative, which is the safe direction, but a real finding that
belongs on the Methods page rather than in a footnote. It is plausibly a
consequence of the heavy shrinkage selected by tuning (λ = 128): a bootstrap
refit re-selects nothing and simply re-fits at the same penalty, so the two
procedures are not measuring quite the same thing. That interpretation is a
hypothesis, not a measurement, and is flagged as such.

Note that the codebase only treats the *narrow* direction as a stated limitation
(`_limitations()` in `trs/pipeline/train.py` adds a bullet for
`analytic_intervals_too_narrow` and not for `..._too_wide`). That asymmetry is
defensible — too-narrow intervals mislead, too-wide ones merely cost sharpness —
but it means this run's verdict does not appear in the artifact's `limitations`
list, only in the diagnostic. It is reproduced here for that reason.

## 7. Encoding assumptions

`trs/features/spec.py` declares the schema; `trs/features/transform.py`
implements it. Current schema version: **`fs-1.0.0`**. A model can only score a
snapshot built under the schema version it was trained on; the loader refuses
otherwise.

63 features across 12 domains, by kind: 22 numeric, 15 ordinal, 13 binary,
11 count, 2 nominal. After encoding, the deployed design matrix has **109
columns** — 61 raw numeric/ordinal/binary/count features, 36 missing indicators,
and 12 one-hot columns from the 2 nominal features (5 non-reference modality
groups and 7 non-reference target-class groups that were observed in the
training partition; levels never observed in training get no column at all).

**Ordinal encodings are assumptions, and they are written down.** Mapping an
ordered category to an integer asserts something about spacing. With cohorts of
hundreds rather than millions, that assumption buys a large variance reduction
over one-hot coding, and it is the right trade — but it is a trade, and each of
the twelve ordinal maps in `ORDINAL_MAPS` carries the scale it encodes.
Non-uniform spacing is used deliberately where a qualitative gap is larger than
an adjacent-tier gap:

- `GENETIC_EVIDENCE_ORDINAL`: no human genetic signal → 0.0, expression QTL only
  → **1.5**. The gap between "human biology speaks at all" and "it does not" is
  encoded as larger than the gaps between adjacent tiers.
- `TARGET_ENGAGEMENT_ORDINAL`: animal direct → 3.0, human indirect PD → **5.0**.
  Engagement demonstrated in humans answers a question animal data cannot, so the
  jump is two steps.
- `REPLICATION_ORDINAL`: same-lab multiple → 1.0, independent lab single →
  **2.5**. Independence is worth more than repetition.

**Where the spacing assumption is not defensible, the feature is nominal.**
Modality and target class are one-hot encoded, after being pooled into groups
(`MODALITY_GROUPS`, `TARGET_CLASS_GROUPS`) so that rare modalities do not each
receive a coefficient estimated from two observations. `small_molecule` and
`kinase` are the reference levels — the most common and best-characterised — so
every other coefficient reads as a contrast against them. The pooling is a
modelling choice with real content (protein degraders are pooled with small
molecules; radiopharmaceuticals with ADCs) and is reproduced in
[MODEL_CARD.md](MODEL_CARD.md) as a limitation.

**Transforms** (`Transform`): counts are `log1p`-transformed, ratios `log2`,
proportions `logit` with clipping at 1e-6. A non-finite value after transform is
treated as missing rather than propagated.

**Standardisation** is fitted on the **training fold only** — as are imputation
medians, one-hot level sets and the imputation pools — then serialised into the
artifact and reused verbatim for calibration, test and production rows. All
three are leakage vectors if fitted on the full dataset. Columns with training
standard deviation below `_SD_FLOOR = 1e-8` are left unscaled rather than
divided by near-zero.

**Effect-size harmonisation.** `standardise_effect()` in
`trs/features/effects.py` maps heterogeneous preclinical readouts (tumour-growth
inhibition, hazard ratios, fold changes) onto one approximate standardised
scale, using a ratio-of-remaining family `d = −ln(1−p)·SCALE` and a log-ratio
family using the Hasselblad–Hedges `d = ln(OR)·√3/π`. This is explicitly a
*comparability device*, not a meta-analytic pooled estimate: the inputs lack the
variance information a meta-analysis requires and the studies are not
exchangeable. The resulting feature should be read ordinally, which is the only
interpretation the transformation supports.

## 8. Missingness policy

Missingness is a modelled quantity, not a default. `MissingPolicy` distinguishes
four cases, and the 63 features split 42 / 16 / 3 / 2 across them:

| Policy | n | Meaning |
|---|---|---|
| `IMPUTE_WITH_INDICATOR` | 42 | Fill with the training median, **and** add a `{name}__missing` column so the model can learn an effect of *not knowing*, separately from the effect of the value. The default wherever silence is informative. |
| `ZERO_IS_ABSENCE` | 16 | Missing genuinely means zero — "count of non-human-primate studies" is 0, not unknown, when the evidence sweep is exhaustive by construction. |
| `IMPUTE_ONLY` | 3 | Fill, no indicator. Used where missingness is near-universal or near-absent, so an indicator would be degenerate. |
| `EXPLICIT_LEVEL` | 2 | For nominal features: "unknown" is a legitimate level with its own column. |

An indicator column is only *created* when the training missing rate falls inside
`INDICATOR_RATE_BAND = (0.02, 0.98)`. Outside that band the indicator is
near-constant and contributes nothing but a penalised coefficient. On the
deployed model, 36 of the 42 eligible features received an indicator; the band
and the per-feature missing rates are serialised into the artifact so the
decision is auditable rather than emergent.

"Not reported" and "not applicable" are different facts. The completeness score
(`compute_completeness`) does not penalise `NOT_APPLICABLE` — penalising it would
mark every monotherapy as incomplete for lacking combination data — and it
weights features by `FeatureSpec.completeness_weight`, so "80% complete" means
"80% of the evidence that actually moves this estimate is present" rather than
"80% of table columns are non-null".

The evidence-confidence grade (`grade_evidence_confidence`) is reported **beside**
the probability and never modifies it. It starts from weighted completeness,
is only ever **downgraded** by additional checks (absent critical domains, fewer
than 5 or 12 evidence items, synthetic provenance), and never upgraded: a narrow
interval on thin evidence is a property of the model, not of the evidence.

## 9. Hyperparameter selection

Hyperparameter selection is a form of fitting, so it happens on
**expanding-window folds inside the training partition only**
(`nested_temporal_folds`). Fold *k* trains on everything before a cut date and
tests on the next slice. This mirrors deployment — always predicting forward —
and, unlike k-fold, never lets a later program inform an earlier one. Tuning
never sees the calibration or test partitions.

`DEFAULT_L2_GRID = (0.25, 1, 4, 16, 32, 64, 128, 256, 512, 1024, 2048)`. The
range is wide on purpose: with ~109 encoded columns and a few hundred training
rows the optimum sits at heavy shrinkage, and an earlier grid that stopped at 64
pinned the tuner to its own endpoint, underfitting and leaving the model
over-confident out of sample. **A grid whose argmin lands on an endpoint has not
selected anything**, so `tune_l2` detects that case, sets
`optimum_at_grid_boundary: true` and writes a warning into the artifact instead
of shipping silently.

On the demonstration run the selected penalty was **λ = 64.0** with a mean
expanding-window log loss of 0.6389 over 4 folds, and
`optimum_at_grid_boundary: false`. The trace is monotone on both sides of the
optimum (0.25 → 1.206, 64 → 0.6401, 128 → 0.6389, 256 → 0.6445, 2048 → 0.6649),
so the selection is interior and well-behaved.

## 10. What would justify moving to full MCMC

PyMC is already declared as an optional dependency (`[project.optional-dependencies] bayes`)
and is deliberately **not** installed by default. The deployed families use an
analytic Laplace posterior, and adding a sampler that is not needed adds fit
time, nondeterminism and a convergence-diagnostics burden to every training run.

Four conditions would each individually justify the switch:

1. **The hierarchical family is adopted and its intervals are published.** The
   variance component `τ²` is currently plugged in at its cross-validated
   optimum, so `N(0, τ̂²)` is treated as known. Integrating over `τ²` is the
   correct fix, and it is not available analytically. Widening the interval by
   an arbitrary factor instead would be an assertion without a basis, which is
   why `hierarchical.py` says so in its own docstring rather than doing it.
2. **`interval_agreement` reports `analytic_intervals_too_narrow` at an
   operating sample size.** That is the empirical signal that the second-order
   approximation has not arrived. (The current run reports the *opposite*
   verdict — 1.88, too wide — so this condition is not met.)
3. **Hierarchy beyond one level.** Nested grouping (indication within
   therapeutic area within mechanism) or crossed random effects push the design
   matrix augmentation past the point where a single ridge precision is an
   honest representation.
4. **Genuinely non-Gaussian posterior geometry.** Near-separable subgroups, or a
   funnel between a group's effect and its variance component, are exactly where
   a Laplace approximation centred at the mode misrepresents the posterior — and
   exactly where a sampler earns its cost.

Until one of those holds, a sampler would add cost without adding honesty. The
condition should be checked at each retraining, not assumed settled.

## 11. Known defects and open weaknesses

Stated here rather than discovered later.

1. **`effective_degrees_of_freedom` is not measuring anything.**
   `L2LogisticRisk.fit` records
   `float(np.trace(H @ self._posterior_cov) - 0.0)` as a diagnostic, but
   `_posterior_cov` is `H⁻¹`, so the trace is identically the design dimension.
   Verified across three penalties on the real training matrix: λ = 1 → 110.0,
   λ = 128 → 110.0, λ = 2048 → 110.0, with *p* + 1 = 110. The intended quantity
   is the ridge effective degrees of freedom,
   `tr[(XᵀWX)(XᵀWX + Λ)⁻¹]`, which would fall with λ. **Nothing in the pipeline
   consumes this field**, so no published metric is affected, but the number is
   meaningless as written and should not be cited.
2. **The Laplace intervals are ~1.9× wider than a bootstrap refit** at this
   sample size (§6.5) and this verdict does not reach the artifact's
   `limitations` list, only its `interval_agreement` diagnostic.
3. **Variance-component uncertainty is not propagated** in the hierarchical
   family (§3.1). This is a known, deliberate limitation, not an oversight.
4. **Specification sensitivity depends on retained candidates.** If
   `register_candidates=False`, the panel silently reports "unavailable". It is
   a configuration foot-gun rather than a statistical defect.
5. **`trs/cohort/outcomes.py` references a module that does not exist.** Its
   docstring points at `trs.modeling.competing_risks` for "the cumulative-incidence
   view when the data support it". `backend/trs/modeling/` contains only
   `base`, `calibration`, `gbdt`, `hierarchical`, `logistic` and `uncertainty`.
   The cumulative-incidence view is therefore **not implemented**, and any claim
   that this platform reports competing-risk cumulative incidence would be false.
6. **The model has no demonstrated skill on the demonstration data.** Held-out
   Brier skill against the cohort base rate is −6.5% with a 95% component
   bootstrap interval of −6.5% to +11.2% — interval includes zero, verdict
   `not_distinguishable_from_base_rate`. The platform says so explicitly in
   every score response. See
   [VALIDATION_PLAN.md §5](VALIDATION_PLAN.md#5-the-usefulness-gate).
