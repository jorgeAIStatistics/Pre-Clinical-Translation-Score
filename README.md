# Preclinical Translational Risk Scorer

The Preclinical Translational Risk Scorer is a decision-support platform that estimates, and
explains, the risk that a preclinical therapeutic program fails to translate into human clinical
efficacy. For a given development track — one program, in one indication, assessed as of one
cutoff date — it assembles structured evidence from public biomedical sources, reduces it to a
declared 63-feature schema, fits a calibrated risk model whose held-out performance is reported
honestly, and returns a probability together with an uncertainty interval, a decomposition of
where that interval's width comes from, an evidence-completeness assessment, and an exact
feature-level attribution whose terms sum to the log-odds of the number on screen. It is **not** a
regulatory instrument, **not** clinically validated, **not** a causal model, **not** a safety or
toxicology predictor, and **not** a substitute for scientific judgement; it reads a preclinical
evidence package and reports what that package currently supports, with its weak joints named.

## 1. Quickstart

Two processes: a FastAPI backend and a Next.js frontend. The backend runs on SQLite by default, so
there are no external services to install.

**Prerequisites:** Python ≥ 3.11 (the checked-in virtualenv is CPython 3.14.5), Node.js ≥ 20, and
`npm`. PostgreSQL is optional — see [Running on PostgreSQL](#running-on-postgresql).

### 1.1 Backend

There is no activated virtualenv in this checkout and none is needed: every command below calls the
interpreter in `.venv` by absolute path. Substitute your own path if your virtualenv lives
elsewhere.

```bash
# From the repository root. Creates .venv if absent, installs the backend
# (editable, with dev extras) and the frontend's node_modules.
make install
```

Equivalently, by hand:

```bash
cd /Users/jorgerodriguez/Desktop/Bioinformatics
python3 -m venv .venv
./.venv/bin/pip install -e "backend[dev]"
```

Create the schema:

```bash
cd /Users/jorgerodriguez/Desktop/Bioinformatics/backend
/Users/jorgerodriguez/Desktop/Bioinformatics/.venv/bin/alembic upgrade head
```

This applies the single migration `05c2a99460a1_initial_schema` and produces 41 tables — 40
application tables plus Alembic's own `alembic_version`. The database URL comes from
`trs.config`, never from `alembic.ini`, so migrations and the application can never disagree about
which database they are pointing at.

Generate the demonstration dataset and train a model:

```bash
cd /Users/jorgerodriguez/Desktop/Bioinformatics/backend
/Users/jorgerodriguez/Desktop/Bioinformatics/.venv/bin/python -m trs.cli pipeline
```

`pipeline` runs `init-db` → `seed` → `build-cohort` → `train` in one command and prints the
held-out metrics at the end. On the default `--programs 600` it takes a few minutes; pass a smaller
value to iterate faster. It is safe to re-run against a fresh database; run it against a populated
one only if you want additional programs appended.

> **`trs.db` and `backend/artifacts/` in this checkout are already populated.** Re-running
> `pipeline` will append to them. If you want a clean run, point `TRS_DATABASE_URL` and
> `TRS_ARTIFACT_DIR` somewhere else, or delete them first.

Serve the API:

```bash
cd /Users/jorgerodriguez/Desktop/Bioinformatics/backend
/Users/jorgerodriguez/Desktop/Bioinformatics/.venv/bin/uvicorn trs.api.main:app --reload --port 8000
```

Check it:

```bash
curl -s http://127.0.0.1:8000/api/v1/health
# {"status":"ok","version":"0.1.0","environment":"development","database":"ok",
#  "active_model":"ptrs-pef-001","feature_schema_version":"fs-1.0.0",
#  "is_demonstration_deployment":true,"development_auth_fallback":true}
```

Interactive OpenAPI documentation is served at <http://127.0.0.1:8000/api/docs>; the raw schema is
at `/api/openapi.json`.

> **`development_auth_fallback: true` is expected in development and refused in production.** When
> `TRS_ENV` is `development` or `test`, an unauthenticated request resolves to the demonstration
> organisation so the UI runs without a login flow. `assert_production_safety()` in
> `trs/api/security.py` refuses to start the application in production if that fallback is
> reachable or if `TRS_SECRET_KEY` is still the development default. The check runs at startup, not
> at first request.

### 1.2 Frontend

```bash
cd /Users/jorgerodriguez/Desktop/Bioinformatics/frontend
npm install
echo 'NEXT_PUBLIC_API_BASE_URL=http://localhost:8000' > .env.local
npm run dev
```

The app is then at <http://localhost:3000>.

`NEXT_PUBLIC_API_BASE_URL` is the one variable the frontend needs. It defaults to
`http://localhost:8000` in `next.config.mjs` and is read **at request time**, not baked in at build
time, so one build can be promoted across environments without a rebuild. A template is checked in

All data fetching happens in React Server Components (`frontend/lib/api.ts`), so the browser never
talks to the API directly and no credentials reach the client bundle.

### 1.3 Configuration

Copy `.env.example` to `.env` at the repository root and edit. Every setting is prefixed `TRS_`
and is read by `trs/config.py`. The ones that matter most:

| Variable | Default | Notes |
|---|---|---|
| `TRS_DATABASE_URL` | `sqlite+pysqlite:///backend/trs.db` | PostgreSQL 15+ is the production target; the ORM and migrations are portable across both. |
| `TRS_ENV` | `development` | `production` hard-disables the unauthenticated fallback. |
| `TRS_SECRET_KEY` | dev-only default | Must be changed for anything but local use. |
| `TRS_ARTIFACT_DIR` | `backend/artifacts` | Where model artifacts are written and loaded from. |
| `TRS_NCBI_API_KEY`, `TRS_OPENALEX_MAILTO`, `TRS_CROSSREF_MAILTO` | empty | Optional, but without them connectors report `degraded` and run in throttled anonymous pools. |

`docker-compose.yml` at the repository root starts PostgreSQL 16 for confirming that the same

```bash
docker compose up -d
export TRS_DATABASE_URL=postgresql+psycopg://trs:trs@localhost:5432/trs
cd backend && alembic upgrade head && python -m trs.cli pipeline
```

This requires the `postgres` extra: `pip install -e 'backend[postgres]'`.

## 2. Make targets

`make` with no argument prints this list.

| Target | What it does |
|---|---|
| `make install` | Creates `.venv` if absent, installs `backend[dev]` editable, runs `npm install`. |
| `make db` | `alembic upgrade head` against `TRS_DATABASE_URL`. |
| `make seed` | Generates the synthetic demonstration dataset (`--programs`, default 600). |
| `make train` | Builds the cohort, then trains, validates, calibrates and registers a model. |
| `make api` | Runs uvicorn with reload on `API_PORT` (default 8000). |
| `make web` | Runs `next dev` on `WEB_PORT` (default 3000). |
| `make test` | Runs the backend test suite. Fully offline: in-memory database, recorded connector payloads. |
| `make lint` | Ruff over `trs` and `tests`; `tsc --noEmit` over the frontend. |
| `make clean` | Removes Python and Next build caches. **Leaves the database, model artifacts and connector cache alone.** |
| `make demo` | Full bootstrap from an empty database: `alembic upgrade head`, then `trs.cli pipeline`. |

Variables are overridable on the command line — `make api API_PORT=8001`,
`make demo PROGRAMS=120`, `make train ENDPOINT=ph2_any_scientific_failure`.

`make lint` prints a notice instead of failing when `ruff` is not present in the virtualenv; `ruff`
arrives with the `dev` extra, so `make install` fixes that. The frontend's `npm run lint` script is
currently broken — `next lint` was removed in Next.js 16 and the argument is now parsed as a
directory name — which is why `make lint` uses `npm run typecheck` instead.

## 4. The five product surfaces

| # | Route | Surface | What it is for |
|---|---|---|---|
| 1 | `/` | **Portfolio** | Every program in the project, each scored as of its own development decision date. Point estimate, 95% interval, evidence-confidence grade, completeness, and the single largest risk driver. The interval is rendered as a bar rather than a footnote, because on this data the intervals overlap heavily and a ranking on point estimates would be a misreading. |
| 2 | `/programs/[id]` | **Program detail** | One track in full: the estimand printed verbatim above the number, the interval and its three-source decomposition, the exact driver attribution, the evidence matrix by domain, the evidence table with per-item provenance, historical comparators, and the scenario panel. |
| 3 | `/evidence` | **Evidence explorer** | The evidence base as a whole rather than one program's slice of it — the feature schema (what the platform is *able* to see), the source vocabulary, and a route into any program's evidence. The diligence surface: what is present, and what is absent. |
| 4 | `/methods` | **Methods & validation** | Generated from the registered model artifact, not written by hand. Leads with the unflattering material: Brier skill against the base rate and whether its interval excludes zero, the attrition waterfall, the effective sample size, the calibration curve, the decision curve, the domain ablation, the coefficient sign audit, and the analytic-versus-bootstrap interval agreement check. This is the page that decides whether a statistically literate reader trusts the product. |
| 5 | `/provenance` | **Data provenance** | Where evidence comes from, whether each source is currently reachable, and what the platform does when one is not. Reachability is presented as a normal operating state rather than an error, because a public biomedical API being unavailable is routine and the honest response is to say so — not to return an empty result that reads as "no evidence found". |

## 7. Known limitations

Ordered by how much they should change your reading of a number.

### 7.1 The registered model is not distinguishable from the base rate

This is the platform's own verdict, recorded in `metrics.usefulness` of the model artifact and
printed at the top of the Methods surface:

> **`not_distinguishable_from_base_rate`** — "The model is not distinguishable from quoting the
> cohort base rate: Brier skill +3.5% (95% CI −6.5% to +11.2%), interval includes zero. Treat
> individual estimates as weakly informative at best."

The artifact also records why this is the threshold question and not a footnote: discrimination
metrics are invariant to monotone distortions of probability, so a model can rank programs
correctly and still produce probabilities less accurate than the base rate. Because this product's
output *is* a probability, skill against the base rate is the question that decides whether it is
useful at all.

**On the current demonstration deployment, no individual estimate should be acted on.** What
remains useful is structural: the exclusion waterfall, the completeness assessment, the evidence
matrix, the provenance chain and the scenario sensitivity each report something the platform
actually knows.

### 7.2 Everything is synthetic

Restating the banner because it is the limitation that subsumes all the others. The data-generating
process is written down in `trs/seed/generator.py` rather than tuned by eye, precisely so a reader
can tell what a model fitted to it is recovering: latent translational properties → a true failure
log-odds → evidence generated as *noisy, incomplete observations* of those latents. That last step
is why the achievable AUROC sits near 0.74 rather than 0.99.

### 7.3 The deployed model's own calibration slope is outside the band that disqualified its challengers

`trs/pipeline/select.py` disqualifies a **challenger** whose calibration slope falls outside
[0.80, 1.25]. The incumbent `l2_logistic` baseline is exempted from that check — it is tested only
against the wider sanity band [0.15, 6.0] — and its held-out slope is 0.733, which is outside the
adoption band. Both challengers were rejected on exactly this criterion. The asymmetry is
deliberate baseline privilege, and on this evidence it is doing real work: had the incumbent been
held to the challenger standard, no family would have passed and training would have failed
loudly. A reviewer should know that the deployed model would not have been adopted under the rule
applied to its rivals.

### 7.4 The analytic prediction intervals are too wide

`interval_agreement` in the validation report re-derives interval widths by bootstrap refit and
compares them with the analytic Laplace widths. Verdict: **`analytic_intervals_too_wide`**, median
ratio 1.88 (p10 1.55, p90 2.44) over 30 probe rows and 40 refits. The Laplace approximation is
asymptotic; at 422 training rows and 109 design columns the asymptotics has not arrived. Intervals
shown to users are therefore conservative by roughly a factor of two — which is the safe direction,
but it is not a correct interval.

### 7.5 The effective sample size is the component count, not the row count

571 cohort rows collapse to 466 independent connected components. Every confidence interval in the
platform is computed by resampling components rather than rows, because rows within a component are
not independent and resampling them as if they were produces intervals too narrow by roughly the
square root of the mean component size. The practical consequence is that the held-out set is
small: 149 rows, of which 83 are positive.

### 7.6 Grouping scope changes the answer

The headline split groups on *identity* (program and compound). A sensitivity analysis that instead
forbids any program sharing a **target** with a test program from appearing in training gives AUROC
0.601 against the headline 0.630. Grouping on mechanism class was rejected as a headline scope
because its transitive closure swallows the cohort and because it would remove from training
exactly the class-level knowledge a real analyst possesses — but the 0.601 figure is the honest
indication of how much of the headline number is target-level memorisation.

### 7.7 The temporal split's test partition is not purely forward

`temporal_split()` assigns a connected component that straddles a date boundary wholly to the
*later* partition. That is the conservative direction for training — no future-resolved sibling can
inform an earlier prediction — but it means 12 of the 149 test rows have as-of dates on or before
the train cutoff of 2017-12-23. The artifact describes these rows as "moved"; the function's own
docstring describes them as "dropped". They are neither discarded nor strictly forward, and the
description should be reconciled.

### 7.8 Several evidence domains contribute nothing measurable

From the domain ablation in the validation report, removing a whole domain and refitting:

| Domain removed | Δ log loss | Reading |
|---|---:|---|
| PK/PD translation | +0.0152 | contributes |
| Reproducibility & study quality | +0.0118 | contributes |
| Target validation | +0.0107 | contributes |
| Animal-model validity | +0.0012 | negligible |
| Safety translation | +0.0006 | negligible |
| Program context | +0.0001 | negligible |
| Evidence volume & recency | −0.0002 | no cost to removal |
| Human biological support | −0.0023 | no cost to removal |
| Cross-species concordance | −0.0024 | no cost to removal |
| Historical class performance | −0.0027 | no cost to removal |
| Biomarker readiness | −0.0051 | no cost to removal |
| Disease-model relevance | −0.0129 | removing it *improves* held-out log loss |

Positive Δ means performance got worse without the domain. Five domains are free to remove and one
is actively harmful on this data. The scorecard presents twelve domains; on the current model, three
of them earn their place. The ablation exists to make that visible rather than to let a
twelve-row scorecard imply twelve contributions.

### 7.9 A leakage channel is deliberately left open

Historical class-performance features exclude post-cutoff outcomes and the focal program's own
siblings, unconditionally. They do **not** exclude other programs that happen to sit in a different
cross-validation fold, because at the historical decision point the analyst genuinely knew those
outcomes and removing them would make the training distribution differ from the deployment
distribution. The consequence — grouped folds are not fully independent through this channel — is
disclosed rather than fixed, and the domain ablation quantifies it. See
[VALIDATION_PLAN.md](VALIDATION_PLAN.md).

### 7.10 Coefficient signs disagree with prior expectation more often than not

The sign audit checked 56 coefficients against the `expected_direction` declared in the feature
registry: **16 are discordant**, of which **0 are credibly discordant** (their intervals include
zero). Expected directions are recorded but never enforced during fitting, by design — a model that
silently enforces the analyst's priors cannot surprise the analyst. On this data the honest reading
is that most coefficients are not distinguishable from zero in either direction.

### 7.11 ClinicalTrials.gov ingestion is unavailable from this network

See [§6](#connector-reachability-verified-from-this-machine-on-2026-09-24). Trial-derived evidence
cannot currently be ingested. The connector's normalisation logic is exercised against
hand-constructed fixtures whose values are illustrative, not real.

### 7.12 Entity resolution runs, but nothing has been ingested through it yet

`trs/resolution/` implements name normalisation and a resolver that links an incoming name to a
canonical entity by strong identifier, registered alias, normalised name, or a conservatively
thresholded fuzzy match — writing an `entity_resolution_decision` row for every attempt, accepted
or refused. Its thresholds prefer a missed merge to a false one, because a false merge puts two
assets into one program and lets that program straddle a train/test split.

What has not happened is a real ingestion run through it. The demonstration dataset is generated
rather than resolved, so the resolver's alias index is populated by the generator (using the same
normalisers, which `tests/unit/test_resolution.py` asserts) rather than by reconciling names from
several sources. Until a connector pipeline actually runs, the review queue stays empty and the
hard cases — one asset under four designations across three sponsors — are exercised only by
tests, not by data.

### 7.13 Survivorship bias is a property of the source data, not of the estimator

Publicly disclosed programs are not a random sample of all programs. Assets abandoned before an IND
are systematically under-represented, so estimates *conditional on entering human development* are
better supported than unconditional attrition estimates. This is why the primary endpoint is
conditional, and why `preclinical_attrition` carries its own standing warning.

### 7.14 The estimate is cause-specific, and reading it as unconditional will mislead

The primary endpoint excludes programs withdrawn for safety, PK/PD, manufacturing or commercial
reasons rather than counting them as efficacy failures. A reader who takes the number as a total
probability of failure will under-estimate total attrition. The conditional clause is printed
verbatim beside the number on every surface for this reason; the composite endpoint
`ph2_any_scientific_failure` exists so the unconditional scientific-attrition question can be asked
directly.
